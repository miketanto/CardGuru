# Phase 9 — engine throughput for RL training

Mandate (`rl/ENGINE-PERF-KICKOFF.md`): make episodes-per-hour go up
without changing game behavior. No modeling, no instrument changes —
driver, harness, JVM and (measured, flag-guarded) engine work only.

**Headline: 0.49 -> 2.72 games/sec on the scripted workload (5.5x
median, range 4.4-6.1x) and 0.48 -> 1.28 games/sec on the policy
workload (2.7x), on the same 4-core container, with the equivalence
gate passing on every step.**
Everything is opt-in behind flags; with no flags set the runners behave
exactly as they did before this phase.

## Environment

XMage pin `7554968c` rebuilt from scratch this session, plus the two
pre-existing local patches (bounded `Combat.getAttackablePlayers` scan;
`benchmark` + `benchmark.rl` test packages) and the Phase 9 patches
below. JDK 21, 4 cores, 15 GB. Engine diffs are exported to
`rl/engine-patches/phase9-engine.patch`; the Mage.Tests sources are
mirrored in `rl/xmage-src/` as usual. `benchmark/xmage/src/` is
untouched — **no player file was modified**, so D0/D1/D1ip remain the
frozen instruments Phase 4/5 calibrated.

## Benchmark protocol (as specified)

Wall-clock for a fixed 100-episode workload, run twice per
configuration on the same container:

- **(a) scripted** — `-Drl.agent=search -Drl.opponent=heuristic`, seed
  960000, BenchDimir mirror, stopTurn 80, consultBudget 4000. No Python
  in the loop.
- **(b) policy** — `-Drl.agent=rl` over the policy server (attn ckpt
  `/tmp/rl_c6_attn_s0/net.pt`, E2 features, cdim 91) vs heuristic, seed
  950000, same deck/stopTurn.

Runner: `bash rl/perf_bench.sh <a|b> <tag> <mvn|persist> [extra -D...]`.
Every row below is a line in `/tmp/rl_p9/bench_log.txt`.
`games_per_sec` is episodes / total wall-clock, so it *includes* the
per-chunk fixed overhead — that is the number a league lane actually
pays.

**Equivalence gate**: workload (a)'s summary must stay within .03
win-rate of the baseline. Baseline (a) is 65 wins / 35 losses / 0 draws
/ 0 stalls, `win_rate=0.6500`, reproduced identically on both runs.
Every configuration below lands in **.65-.67** (max deviation .02).
Note the summary is *not* bit-identical across JVMs even at a fixed
seed — the two baseline runs differ in `turns_per_ep` (17.3 vs 17.4)
and search nodes (4414 vs 4432) — so "identical wins/losses, win_rate
within jitter" is the strongest available form of the gate, and it is
what every row here meets.

## Where the time actually goes

JFR (`settings=profile`, `stackdepth=512`) over a 50-episode conc4
scripted run; collapsed stacks, hot-method table and a flame graph in
`rl/perf/` (`scripted.svg`, `scripted.top.txt`,
`scripted.collapsed.gz`), generated by `rl/jfr_flame.py` (async-profiler
is not installable here, so this is JFR + a small renderer). 4643
samples on game threads.

Inclusive time:

| share | frame |
|---|---|
| **82%** | `PlayerImpl.getPlayable` |
| 72% | `GameImpl.createSimulationForPlayableCalc` (the full state copy *inside* getPlayable) |
| 42% | `getManaAvailable` / `ManaOptions` |
| 56% | reached via `HeuristicPlayer.priority` |
| 34% | reached via `SearchPlayer.searchBest` |
| **2.8%** | `createSimulationForAI` — the D1 search sims |
| 0.3% | `GameStateEvaluator2.evaluate` |

Self time is almost entirely copy constructors: `ManaOptions.<init>`
11.4%, `Mode.copy` 9.9%, `ManaCostsImpl.<init>` 8.3%, `Effects.<init>`
5.2%, `CardUtil.deepCopyObject` 4.9%.

**This corrects a standing assumption.** The kickoff expected
`Game.copy()` inside `createSimulationForAI` to be a main cost; at D1
(1 ply x breadth 8) it is 2.8%. The real cost is that *every*
`getPlayable` call deep-copies the whole game state, and the seats call
it constantly. Deck loading, the state encoder, and the NDJSON policy
consult are all <1% — the kickoff's read that IPC is not the bottleneck
is confirmed.

The single biggest piece of waste is structural: **27.7% of game-thread
samples are the D1 seat computing `getPlayable` twice on the same
untouched state** — once in `SearchPlayer.searchBest`, then again in the
`HeuristicPlayer.priority` it delegates to when the search declines to
act. That is what optimization 4 targets.

## The changes

### 1. Persistent driver JVM (`RLDriverServer` + `driver_client.py`)

`RLEpisodeDriver`'s episode loop moved verbatim into a new
`EpisodeRunner`; the `@Test` now delegates to it, so the mvn path is
unchanged (verified: a post-refactor mvn run reproduces 66/34, .66, and
an in-loop 0.527 games/sec against the baseline's 0.512/0.545).

`RLDriverServer` is a plain `main` that pays the one-time costs once —
`MageTestPlayerBase.init()` (game types + plugin classloader),
`CardScanner.scan()`, `DataCollectorServices.init()`, ~8-40s depending
on disk cache — then serves jobs on a localhost socket. **A job line is
literally the `-D` list the mvn command took**, which is what makes the
runner change a one-line substitution. It streams the driver's stdout
back and ends each job with `RLJOB|done|rc=N`.

Design points worth keeping in mind:

- Jobs are **serialized**; parallelism lives *inside* a job
  (`rl.concurrency`), so a job's summary line is still one workload.
- `rl.*` properties are **cleared between jobs** — a stale
  `-Drl.imitateOut` from the previous chunk would otherwise keep
  logging.
- Four properties are read into `static final`s downstream
  (`rl.cardFeatures` fixes `StateEncoder.CAND_DIM` at class load, plus
  `rl.phi`, `rl.noYields`, `rl.debug`). The server **pins them on the
  first job and refuses** a later job that changes them, rather than
  silently running with the old value. This fired for real during
  benchmarking when a workload-(a) server was handed a workload-(b)
  job — one server per encoder configuration.
- cwd must be `Mage.Tests`: decks and `config/config.xml` resolve
  relative to it, exactly as surefire's working directory did.

Measured win on its own: **1.09x** on (a), 1.11x on (b). Modest,
because the warm per-chunk overhead is only ~12s — the kickoff's
"1-2 min" figure includes a cold card-DB build, which the `db/`
directory only pays once. The persistent JVM's real value is that it is
the *carrier* for everything below: JIT warmth (a fresh server's first
100-episode job runs ~15% slower than its second — 60s vs 50s, 52s vs
45s) and a place to put concurrency.

### 2. Concurrent games in one JVM (`rl.concurrency=N`)

N worker threads pull episode indices off a shared counter. Episode i
keeps its seed (`seed+i`) and its play/draw parity (`i%2`), so the *set*
of games played is exactly the sequential set — only the order they
finish in changes. Two things were needed to make it correct:

- **Thread naming.** XMage gates game code by thread name
  (`ThreadUtils.isRunGameThread`: only `main`, `GAME*`, `AI-SIM-*`);
  worker threads first died in `checkConcede` with "game related code
  must run in GAME thread". Naming the workers `GAME rl-episode-N` is
  the fix the engine itself documents — **no engine patch needed**.
- **`RandomUtil` is one process-global `Random`** (the kickoff flagged
  this as an open question — confirmed, it is global). Concurrent games
  would shred each other's stream. Patched to an opt-in
  `ThreadLocal<Random>` under `-Dmage.randomPerThread=true`, read into a
  `static final` so the branch folds away; default false is the original
  shared instance, bit-for-bit. With per-thread streams and one episode
  per thread, per-episode determinism is preserved.

Audit of our own classes for shared-static crosstalk, as the kickoff
asked: `RLPlayer`/`SearchPlayer`/`SearchPlayerIP`/`TeacherLogPlayer` keep
all mutable state per instance (counters, `benchSeed`, `decisionCounter`)
and players are constructed fresh per episode; `HeuristicPlayer`'s
statics are constants and pure helpers; `StateEncoder`'s statics are the
immutable feature table. The only shared mutable statics are
`RandomPlayer.decisions/PLAYABLE_HIST/actionsTaken`, which are
metrics-only and used solely by the random-opponent lane — racy counts
there, nothing else. `MageTestPlayerBase.loadedCardInfo` (a plain static
`HashMap` mutated by `Deck.load`) is replaced by a per-runner
`ConcurrentHashMap` with the load itself under a lock.

Scaling on 4 cores: 2.21x at N=2, **4.14x at N=4**, and it *regresses*
past core count (3.4x at N=6, 3.6x at N=8). **N = core count** is the
setting.

The policy lane needed a matching server change: `policy_server.py` grew
`--threads N` (default 1 = the original one-connection-at-a-time loop,
untouched). With N>1 each connection gets a `Session` holding its own
trajectory buffer and LSTM hidden state; on `end_episode` the session's
steps are spliced into the PPO buffer as **one contiguous block**, so
every trajectory PPO sees is still a whole episode in order. One lock
guards inference and the buffers — fine, because engine work dwarfs it.
Validated end to end: a 64-episode `mode=train` chunk at conc4 produced
the expected two PPO update rows in `train.csv` (updates at 32 and 64
episodes, win_rate .547).

**Determinism caveat, stated plainly:** with `--threads>1` in *train*
mode the order episodes enter the PPO batch is scheduler-dependent, so a
training run is no longer bit-reproducible from its seed. Eval and Elo
lanes must stay sequential (`rl.concurrency` unset, server `--threads 1`)
— that is the kickoff's "training lanes only" rule, and `run_driver.sh`
makes it explicit by requiring `RL_CONC` to be set per call.

### 3. GC / JIT

GC is not a major cost, but ParallelGC is the better fit. Two
100-episode conc4 runs per collector, `-Xlog:gc`:

| collector | wall (2 runs) | GC pauses | total pause |
|---|---|---|---|
| G1 (default) | 60s / 50s | 524 | 5.5s |
| ParallelGC | 52s / 45s | 338 | 3.5s |
| ParallelGC + `-Xmn2g` | 49s / 53s | 244 | 3.7s |

ParallelGC cuts pause time ~36% and is a few percent faster wall-clock;
a bigger young gen trades pause count for pause size and is a wash.
Recommendation: `-XX:+UseParallelGC`, leave sizing alone. Note run-to-run
variance (~10%) is of the same order as the collector difference, so
this is the weakest of the four wins — it is adopted because it is free
and never hurt, not because the evidence is strong.

JIT warmup is the bigger JVM-level effect and it is already captured by
the persistent server: first job ~15% slower than subsequent ones.

### 4. `getPlayable` memo (`-Dmage.playableCache=on|verify|off`)

The one engine-semantics change, and the one with the most validation
behind it. `PlayerImpl.getPlayable` keeps its last result per player,
keyed on a fingerprint of everything it reads: the apply-effects
counter, turn/phase/step/step-part, active and priority player, stack
size and top object, and per player life, hand card ids, library /
graveyard / exile sizes, mana pool, plus every permanent's id,
zone-change counter and tapped / phased / face-down / summoning-sick
flags. Any difference misses. The original code path is untouched and
still the default (`off`); the returned list is a fresh `ArrayList` and
all three seats copy an ability before activating it, so sharing the
ability objects between two consecutive calls is safe.

`verify` mode is how the equivalence claim was *tested* rather than
asserted: it serves the cached answer **and** recomputes from scratch,
throwing if the two disagree. Results:

| verify run | hits | misses | mismatches |
|---|---|---|---|
| 100 eps, agent=search vs heuristic, conc4 | 55,786 | 105,883 | **0** |
| 40 eps, same, conc4 | 37,252 | 66,629 | **0** |
| 30 eps, agent=searchip K=4 vs search, sequential | 29,635 | 50,470 | **0** |

That last row matters: it exercises the determinized seat, whose sims
re-randomize hidden zones, and the memo still never disagreed. The
100-episode verify run also reproduced `win_rate=0.6500` — the baseline
exactly.

Measured win: conc4 goes from 50s/48s to 46s/38s (**+13-20%**), hit rate
~35% of `getPlayable` calls.

**Important scoping result:** the memo only pays where a seat calls
`getPlayable` twice on one state, which is the search seats. On the pure
policy lane (agent=rl vs heuristic) it recorded **0 hits in 207,830
calls** — the RL seat consults once per window. Its cost when it cannot
hit is within run-to-run noise (workload (b): 73s/83s with, 100s/80s
without), but there is no reason to pay it: enable `playableCache` on
lanes that have a search/teacher seat, leave it off on rl-vs-rl and
rl-vs-heuristic lanes.

### 5. One real concurrency bug, found and fixed

Roughly 1 concurrent job in 15 died late with a
`ConcurrentModificationException` out of
`GameImpl.initGameDefaultHelperEmblems` ->
`TokenRepository.findPreferredTokenInfoForXmage`. Cause:
`TokenRepository.init()` is an unsynchronized lazy initializer guarded
by "allTokens is not empty" — it assigns the list, *then* builds the
by-type/by-class indexes, so a second thread entering during that window
sees the guard satisfied and streams a half-built index.

Fixed harness-side, with no engine change: `RLDriverServer` and
`EpisodeRunner.runConcurrent` force `TokenRepository.instance.init()` to
completion before any worker thread starts (it is idempotent once
loaded). Confirmed by a 6 x 100-episode conc4 loop with zero failures
after the fix, against a reproduction before it. `EpisodeRunner` also
now logs the failing episode index, seed and stack for any future
worker-thread failure.

This is the kind of latent lazy-init race the kickoff's "verify no
shared-static crosstalk" instruction was pointing at — it just lived in
the engine's repositories rather than in our classes.

## Recommendation for the league runners

Start one server per training session, then swap the mvn line. No runner
has been modified — the kickoff asked that the main session's runners
keep working unmodified until it adopts this — so the change is opt-in
per lane, one line each.

```bash
# once per session (drop -Dmage.playableCache=on for rl-vs-rl lanes)
bash rl/driver_server.sh start 7910 \
    "-Dmage.randomPerThread=true -XX:+UseParallelGC -Dmage.playableCache=on"

# in the runner, replace the mvn invocation
#   mvn -q -pl Mage.Tests surefire:test -Dtest='RLEpisodeDriver' \
#       -DargLine="-Dfile.encoding=UTF-8 -Xmx4500m" -DfailIfNoTests=false \
#       -Drl.episodes=64 ... > /dev/null 2>&1
# with
    RL_PERSIST=1 RL_CONC=4 bash rl/run_driver.sh \
        -Drl.episodes=64 ... > /dev/null 2>&1

# eval / Elo probes in the same runner: same line, RL_CONC UNSET
    RL_PERSIST=1 bash rl/run_driver.sh -Drl.episodes=100 -Drl.mode=eval ...

# policy lanes additionally need the server to accept N connections
python3 rl/policy_server.py --port $APORT --ckpt $CK --threads 4 ...
```

`run_driver.sh` with `RL_PERSIST` unset execs the original mvn command,
so a runner converted this way still runs the old path by default.

Expected effect on a league lane: a 64-episode training chunk that took
~6-8 minutes of games plus ~1-2 minutes of overhead becomes ~1.5-2.5
minutes total (2.7x on the policy lane at conc4, 3.0x at conc6; the
D1-teacher and ladder lanes, which are workload (a) shaped, get 5.5x).
Eval probes stay sequential and therefore stay at ~1.1x — that is the
deliberate price of keeping Elo comparable.

## Honest limits

- Workload (b)'s wall-clock varies ~±20% run to run (policy server +
  torch scheduling), so its speedup figure is coarser than (a)'s.
- The memo's fingerprint is conservative but hand-written; `verify` mode
  is the guard, and it should be re-run whenever a lane uses a card pool
  or format this phase did not exercise (everything here was the
  BenchDimir mirror).
- `rl.deckCache` (parse each .dck once per JVM) is implemented and
  flag-guarded but never measured as its own row — deck loading is <1%
  of the profile, so it was not worth a benchmark slot. Default off.
- Concurrency with `rl.opponent=rl` (two policy seats) is rejected at
  runtime: the opponent seat shares a single policy connection. Wiring
  per-thread opponent connections is the obvious next step for the
  self-play league lanes, and is the main reason those lanes cannot use
  conc4 today.
