# FRA primitive vocabulary — derived from the tallies

Source: `TALLIES.md` (generated by `tally.py` from Forge 2.0.15 scripts).
Mapping code: `signals.py`. This file records *why* each primitive exists
and what was deliberately left out. It was written and committed **before**
the graph was built (see §4).

## 0. Data and coverage

- **Scryfall is unreachable** from this container (`api.scryfall.com`
  CONNECT → 403, network policy). Forge scripts carry `ManaCost`, `Types`,
  `PT`, `Oracle`, keywords — every field the plan wanted from Scryfall
  except collector metadata. Forge is the only source used.
- Forge `forge-2.0.15` (`b18e110`), edition file `Reality Fracture.txt`.
  `[cards]` lists **280 unique non-basic names** (the "~372" figure counts
  variant printings: borderless, echoed-pair, shattered-mirror, etc.).
- **Coverage is complete: 280/280 names resolve to a script** (249 in
  `cardsfolder/upcoming/`, 31 reprints). Two cards have no abilities or
  keywords at all (both Yargles — vanilla by design, not missing).
- The booster-sheet sections of the edition file contain three name typos
  (`Overwrite the Multivers`, `Lyla, Tolarian Archangel`,
  `Winter, Tormented Lover`); `[cards]` is canonical.
- Forge's `DeckHas:` / `DeckHints:` / `DeckNeeds:` lines are hand-authored
  synergy labels (38 / 37 / 4 cards). They are **held out**: not an input,
  used only as an independent check (§5 of the result doc).

Two set mechanics show up only as Forge-internal names, which a keyword
list would not surface:

- **Empower** (`DB$ Empower | Type$ Jace | Num$ 2`, 35 cards): put N
  loyalty counters on a planeswalker *token* of that type, creating it
  first if needed. It is the set's main loyalty source, not `PutCounter`.
- **Prepare** (`AlternateMode:Prepare`, 21 cards + `AlterAttribute
  Prepared`): a creature with an attached spell face that can be cast as a
  copy while the creature is prepared.

## 2. The vocabulary (`signals.EVENTS`)

Each primitive is a state change the tallies show the set actually
touching. The object it concerns is a pattern parsed from Forge filter
syntax (`Creature.Other+YouCtrl` → types {Creature}, side you), so the
same primitive can match narrowly or broadly.

| primitive | emitted by (API / cost / keyword) | listened for by |
|---|---|---|
| `enter` | Token, Empower (PW token), ChangeZone→Battlefield, intrinsic for every permanent | ChangesZone `→Battlefield` (non-self), Count$Valid, ConditionPresent/IsPresent, Continuous `Affected$` anthems, Sac/tapXType costs (fodder), Convoke |
| `die` | Sac costs, Sacrifice (you), Destroy/DamageAll/Fight (removal) | ChangesZone `Battlefield→Graveyard`, ThisTurnEntered_Graveyard_from_Battlefield |
| `tograve` | Mill, Surveil, Discard, ChangeZone→Graveyard, Cycling, intrinsic for instants/sorceries | Count$ValidGraveyard, Threshold, ExileFromGrave costs, ChangeZone from Graveyard, Flashback, ActivationZone$ Graveyard |
| `reenter` | ChangeZone Graveyard/Exile→Battlefield | self-ETB triggers (61 cards) |
| `cast` | intrinsic for every non-land card (Prepare spell faces tagged `prepared`) | SpellCast, Prowess, ThisTurnCast |
| `cast_target_own` | SP$ Pump/PutCounter/Animate targeting a creature | SpellCast `IsTargeting Creature.YouCtrl`, BecomesTarget |
| `counter+` (sub = type) | PutCounter(All), Empower (LOYALTY), `AddCounter<n/LOYALTY>` costs, etbCounter, Proliferate | CounterAdded(Once), R:AddCounter, `SubCounter` costs (fuel), `counters_GE1_P1P1` statics, CardCounters counts |
| `activate_loyalty` | every loyalty ability; Empower tokens | AbilityCast `Activated.Loyalty`, ThisTurnActivated Loyalty |
| `lifegain` | GainLife, Lifelink | LifeGained, LifeYouGainedThisTurn |
| `draw` / `discard` | Draw / Discard (you), Cycling | Discarded; discard costs and ValidHand counts consume `draw` |
| `scry` / `surveil` | Scry / Surveil | Scry / Surveil triggers, YouScry/SurveilThisTurn |
| `prepare` | AlterAttribute Prepared on another object | every Prepare card |
| `mana` (resource) | non-land Mana abilities, lands making ≥2, mana tokens (Treasure, Lotus, Heartwood), land ramp | MV ≥ 5, X in cost, xPaid, non-loyalty activated costs ≥ 4 or with X |
| `cost_mod` | S:ReduceCost/RaiseCost with a non-self `ValidCard$` | any card matching the filter |

Three edge types fall out of the vocabulary rather than being declared:
**shared state** (every primitive except the two below), **resource flow**
(`mana`), **cost modification** (`cost_mod`, Convoke, and self-ReduceCost
whose `Amount$` is a `Count$` — the count becomes the listener).

## 3. Left out on purpose

- **Phase triggers** (18 cards: upkeep, end step) — a clock, not a state
  change another card causes. They produce no edges.
- **Evasion / combat keywords** (Flying, Trample, Vigilance, Menace, Reach,
  Deathtouch, Haste, Ward, First/Double Strike, Defender) — no card in the
  set listens for them. Equip/Enchant are also not listeners.
- **Opponent-side listeners** (`OppCtrl`, `ValidActivatingPlayer$
  Opponent`) — interaction, not synergy. Dropped at the listener.
- **Numeric qualifiers** (`powerGE4`, `cmcLE2`) are parsed but ignored:
  the pattern matches on types only.
- **Oracle / SpellDescription text** is not used anywhere in matching.
- `DeckHas` / `DeckHints` — held out (§0).

## 4. Pre-registration (written before the graph existed)

What the construction **cannot** do, so a result on any of these is a bug:

1. No edge can involve a primitive absent from §2. In particular no edge is
   ever justified by Phase, Flying, Trample, etc.
2. Resource-flow edges never read keywords or oracle text. The Chandra
   validation (plan check 3) is therefore **incapable of passing because of
   a shared keyword**; if a Chandra neighbour's reason mentions one, that is
   a bug.
3. `DeckHas`/`DeckHints` are not read by `signals.py` or the graph builder
   (they are copied into `fra_signals.json` only for the evaluation). No
   weighting scheme can be tuned against them; the held-out agreement is
   reported for all four schemes as they were first written.
4. Empower's counters go on a *token*. A planeswalker **card**'s
   `SubCounter<LOYALTY>` fuel listener requires a nontoken self pattern, so
   Empower → (e.g.) Chandra, Torch of Defiance must **not** appear as a
   `counter+:LOYALTY` edge. If it does, the token/self rule is broken.
5. The uniform scheme ignores tightness and rarity, so it cannot rank a
   lonely pair above a generic one except by coincidence of count.

Expected but not guaranteed (the plan's validation): surveil ↔ graveyard
payoffs co-cluster; loyalty adders → the `CounterAddedOnce:LOYALTY` card;
Chandra's `+1: RR` → top end / X spells.

## 5. Corrections after the first graph run

The sections above are unchanged from the pre-registration commit.
Mapping fixes made afterwards are listed in `SYNERGY-GRAPH.md` §7. Two of
them change rows of the §2 table:

- `cost_mod`: **RaiseCost no longer emits an edge.** It is a tax on the
  matching cards, so it is anti-synergy.
- `counter+` listeners: `R:AddCounter` reads `ValidCounterType$`. `Count$`
  no longer matches `ReplaceCount$` / `TriggerCount$`, and inline `Count$`
  in ability params is now read. Host-attached triggers (`AttachedBy`,
  `EnchantedBy`, `EquippedBy`) are no longer cross-card listeners.
- Statics and replacements granted through `Effect` (SVar `Mode$`/`Event$`
  lines with no `Execute$`) are now routed as `S:`/`R:` lines. New mappings:
  `CastWithFlash` for loyalty abilities → listen `enter` on those
  planeswalkers; `IgnoreLegendRule` → listen `enter` Legendary;
  `AdjustLandPlays` → emit `mana` (ramp). A `Continuous` whose `Affected$`
  names an effect-chosen object or a player is not a population listener.
  See `SYNERGY-GRAPH.md` §10.
- `mana` (resource): the consumer side is no longer "MV ≥ 5". Every nonland
  card with MV ≥ 2 is a candidate, kept only if a producer saves it at
  least a turn (turns-saved model, `SYNERGY-GRAPH.md` §11). `Count$xPaid`
  counts only when X is in a mana cost, not in `SubCounter<X/LOYALTY>`.
