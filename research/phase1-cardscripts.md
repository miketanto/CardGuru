# Phase 1 — Forge card scripts as a mechanical-search ontology

**Verdict: the key insight holds.** Forge's `cardsfolder` is a near-complete, hand-curated
semantic parse of the card pool, its vocabulary is closed and Zipfian, the ability graphs are
real and machine-traversable, and a ~200-line Python parser was enough to run structural
queries Scryfall cannot express. The Phase 1 kill criterion did **not** fire.

Everything below was measured by running code in this session, not quoted from documentation.

- Source: `Card-Forge/forge` @ commit `670429bf9f77c06ac866003604205d9de3413e52` (master, 2026-08-06).
  This is the version pin for all numbers in this document.
- Parser: `research/scripts/parse_cardsfolder.py` (no dependencies, ~4s runtime).
- Outputs: `research/data/ontology.json`, `research/data/stats.json`,
  `research/data/mech_search_results.json`. The full per-card graph file (`cards.jsonl`, 37 MB)
  is regenerated by the parser and not committed.

## 1. Parser status and coverage

| Measure | Value |
|---|---|
| Card script files | 33,574 |
| Card faces after splitting `ALTERNATE`/`SPECIALIZE` blocks | 34,519 |
| Faces with scripting (ability lines and/or keywords) | 34,124 (98.9%) |
| Faces with no ability lines | 395 — of which 363 are true vanillas (empty Oracle) |
| Faces whose scripts reference `Count$` | 5,409 (15.7%) |

The format parses cleanly: `Key:Value` lines; ability lines (`A:`, `T:`, `S:`, `R:`) are
pipe-delimited `Param$ Value` lists; `SVar:` defines named nodes; `K:` lines are keywords.
Multi-face cards (split/adventure/transform/MDFC) are separated by `ALTERNATE` markers in the
same file. No hand-written-Java escape hatch exists at the card level in current Forge — cards
are either scripted in the DSL or absent from `cardsfolder`. (Effect *semantics* live in Java,
but per-card logic does not.)

### Coverage against the canonical card pool

Scryfall's API is blocked by this session's network policy, so the join used the
MTGJSON-derived index vendored in `taw/magic-search-engine` (35,829 unique card names,
including un-sets and digital-only cards) — `research/scripts/join_scryfall.py`.

- **34,228 of 35,829 canonical names matched a Forge face directly (95.5%).**
- Of the 1,601 unmatched: ~625 are acorn/un-set-only cards, plus Alchemy variants,
  Mystery Booster playtest cards, Hero's Path/scheme/plane/vanguard non-playables, and
  alternate-name printings (e.g. "Arvad of the Weatherlight" exists in Forge as
  "Arvad the Cursed"). After filtering those categories the residual "real missing" list is
  ~645 names, and inspection shows it is still dominated by non-tournament product.
  **Effective coverage of tournament-playable cards is ≳99%.**
- 291 Forge-only names are Alchemy rebalances (`A-` prefix) and naming variants.

Caveat: the vendored index lacks per-format legality fields, so an exact legality-weighted
coverage number needs the real Scryfall bulk file once network access is available. The join
itself (normalize name → attach oracle text, types, printings) is demonstrated and trivial.

## 2. The mined ontology (empirical, not hand-authored)

Full counts in `research/data/ontology.json`. Distinct vocabulary sizes at the pinned commit:

| Vocabulary | Distinct values | Top entries (count) |
|---|---|---|
| Effect APIs (`SP$`/`AB$`/`DB$`) | **191** | ChangeZone 6596, Pump 4967, Draw 3710, Token 3554, PutCounter 3269, DealDamage 2847, Mana 2496 |
| Trigger modes (`T:Mode$`) | **137** | ChangesZone 7508, Phase 2359, Attacks 1598, SpellCast 1399, DamageDone 871 |
| Static modes (`S:Mode$`) | **138** | Continuous 5605, CantBlockBy 618, ReduceCost 588 |
| Replacement events (`R:Event$`) | **34** | Moved 957, DamageDone 218, Untap 155, Counter 117 |
| Keywords (`K:`) | **252** | Flying 3293, Enchant 1262, Trample 1033 |
| Parameter keys | 1,206 | — |
| `Count$` functions | 207 | Valid 1921, xPaid 935, ValidGraveyard 463 |

The distributions are strongly Zipfian: 28 of 191 APIs, 44 of 137 trigger modes, and 103 of
207 Count functions occur ≤2 times. Practical consequence: **a CR-mapping effort (Phase 3)
that covers only the top ~50 APIs and ~30 trigger modes already covers the overwhelming
majority of ability instances**, and the long tail can be flagged "unmapped" honestly rather
than silently mishandled.

## 3. The ability graph is real

Nodes = ability lines + `SVar` definitions; edges = `Execute$`, `SubAbility$`,
`StaticAbilities$`, and any parameter whose value names an `SVar` (kept with its parameter
name as the edge type). Ragavan parses into exactly the graph the project brief sketched.

Graph sizes across 34,519 faces: median ~2–3 nodes; 300 faces have ≥10 nodes; the largest is
Urza, Academy Headmaster at 109 nodes. Edge distribution: 10,712 faces have zero edges
(single-node abilities, keywords, vanillas), ~24k have at least one.

## 4. The `Count$` escape hatch, measured

- 5,409 faces (15.7%) use at least one `Count$` SVar; 207 distinct function heads.
- Semantics live in `forge-game/.../AbilityUtils.java` (`xCount`, ~2,400 lines within a
  3,942-line file). The wiki's warning is accurate: this is code, not data.
- **But the tail is manageable.** The `Valid*` family (Valid, ValidGraveyard, ValidHand,
  ValidLibrary — "count objects matching selector X") accounts for ~2,700 of the 5,409 uses,
  and its argument is the *same* Valid-selector language used by `ValidTgts$`/`Affected$`
  everywhere else, so a selector parser pays for itself twice. `xPaid` (935) is just "X paid."
  103 of 207 functions occur ≤2 times.
- For *search*, `Count$` rarely blocks anything: the graph shape (trigger → effect chain) is
  intact; the Count node is an opaque "dynamic quantity" annotated with its function head.
  It matters when a query asks about the *meaning* of the quantity, which is a minority of
  mechanical queries. For Phase 3 CR-mapping it is real work, priority-ordered by frequency.

**Phase 1 kill criterion verdict: does not fire.** Scripting is near-universal (98.9% of
faces), `Count$` touches only 15.7% of faces and mostly via one interpretable family, and the
graph queries below demonstrably exceed oracle-text search.

## 5. Mechanical search prototype — three queries Scryfall can't express

`research/scripts/mechanical_search.py`, running over the parsed graphs. Results in
`research/data/mech_search_results.json`.

**Q1 — "combat-damage-to-a-player trigger whose effect chain creates a token" — 101 cards.**
Subgraph match: `T[Mode=DamageDone, CombatDamage=True, ValidTarget~Player]` with reachability
via `Execute$`/`SubAbility$` to a node with `api=Token`. Finds Ragavan, Old Gnawbone,
Grim Hireling, Brood Sliver… A Scryfall oracle regex (`o:/deals combat damage to a player/ o:token`)
both over-matches (cards where the token clause is a different ability) and under-matches
(triggers templated differently); the structural query pins trigger and effect to the *same
ability chain*. (My test expectation "Brazen Freebooter" was wrong — it's an ETB trigger, and
the query correctly excluded it. Precision working as intended.)

**Q2 — "impulse exile: exiles from the top of the library and lets you play/cast it" — 287 cards.**
Reachability from one ability root to both (a) a `Dig`/`DigUntil`/`Mill`/`ChangeZone` node with
Exile destination and library origin, and (b) a `Continuous` static with `MayPlay=True`.
Finds Ragavan, Light Up the Stage, Outpost Siege, Bonehoard Dracosaur, all the Chandras.
Scryfall has no way to say "the exiled card becomes playable" — wordings vary enormously
("you may play it", "you may cast that card", "until end of your next turn…").

**Q3 — cost-structure query: "activated ability whose cost includes sacrificing a creature and
whose effect adds mana" — 39 cards.** Matches `AB$ Mana` nodes whose `Cost$` contains
`Sac<…Creature>` (or self-sac by a creature). Finds Phyrexian Altar, Ashnod's Altar, Blood Pet,
Phyrexian Tower, Soldevi Adnate… Scryfall cannot separate cost text from effect text at all —
`o:sacrifice o:add` matches hundreds of irrelevant cards.

All three ran in seconds over the full pool in pure Python with no index. A real backend can
precompute node/edge postings; performance is a non-issue at this scale (~35k graphs, median
3 nodes).

## 6. Caveats confirmed

- **Implementation ontology, not rules ontology** — confirmed. `DB$ ChangeZone` conflates
  destroy-and-reanimate, bounce, tuck, exile; `Pump` covers both P/T changes and ability
  grants. The Phase 3 mapping layer is real intellectual work. The mined frequency table is
  the correct priority order for doing it.
- **DSL evolves with the engine** — confirmed; pin `670429bf` (or a tagged release) and record
  the pin in every derived artifact.
- **Naming**: Forge names sometimes differ from canonical names (promo/variant names,
  `A-` Alchemy prefixes). A name-normalization + alias table is needed; ~1–2% of joins.
- **XMage as second extraction source (Phase 1b)**: XMage cards are Java classes
  (32,047 files in `Mage.Sets`); extraction = AST parsing. Deferred — Forge alone proved
  sufficient for search. Worth revisiting for cross-engine disagreement as a QA signal.

## 7. How to reproduce

```bash
git clone --depth 1 --filter=blob:none --sparse https://github.com/Card-Forge/forge.git
cd forge && git sparse-checkout set forge-gui/res/cardsfolder
python3 research/scripts/parse_cardsfolder.py <path-to-cardsfolder> research/data
python3 research/scripts/mechanical_search.py
```
